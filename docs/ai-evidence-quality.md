# AI第5阶段：有证据的异常解释与经营建议

本阶段仅改进分析质量、确定性规则和证据检查，复用既有销售/客户/商品/库存/工单工具。不增加业务工具、预测模型、数据库结构、依赖或框架。模型可以规划总体销售查询并提出重新核对要求，不能生成金额、比例、缺料量、对象ID或因果结论。

## 证据和报告

`AnalyticsEngine`保留Decimal算术，新增`EvidenceEngine`将结论绑定至已校验的工具输出。每条展开证据包含：结论ID、指标定义、具体对象或范围、实际左闭右开日期、Asia/Shanghai、工具查询时刻、当前值、比较值、计算方法、具体工具名和来源。相邻等长上期也写出实际日期；库存类的范围是当前查询时刻，不伪装为历史期间。

报告保留可核对的原始数值表，随后区分：

1. **已经查询确认的事实与证据**：例如含税已发货销售额变化、客户Top1占比、某仓库某物料低于最低库存、某确认工单的缺料。
2. **仍需核实的可能解释**：必须标“待核实”，并引用事实ID，不把集中发货、大单影响或竞争库存当成已确认原因。
3. **建议采取的行动**：引用事实ID，写明具体期间、指标差额或客户/商品/仓库/物料/工单对象；不提出无来源的增长目标、采购优化或自动业务动作。
4. **尚未回答与数据限制**：明确缺少哪项证据，少样本、零分母或权限/工具故障不能被隐藏成零值或完整成功。

销售额和订单增长率在非零基数时只是可重算的历史算术描述；少样本不据此判定明显变化或推断未来。上期为零（含0/0）不计算增长率。首末日差仅比较两个已查日，不称趋势预测。客户集中度在订单不足或分母为零时不计算比率；客户数过少时Top3不作风险预警。无预警与证据不足是不同情况，原始无匹配/无缺料结论仍由对应工具的完整范围说明。

销售下降不能直接归因于缺货。即使当前库存为零，也不能证明历史销售期间缺货，更不能证明订单因缺货未成交。当前工具没有历史缺货、履约受阻及因果识别证据，报告明确将此列为未回答，最多提出待核实假设。待入库不能计入现有库存，多个工单需求未预留，已领料工单不再次计算补料，原第4阶段规则保留。

## 集中配置的规则

唯一规则入口为`agent/app/analysis_rules.py`，版本`evidence-v1`。配置由代码控制，不接受模型或HTTP参数修改；单元测试可注入规则对象。报告打印实际规则版本与阈值。

| 检查 | 默认规则 | 不足时处理 |
|---|---|---|
| 销售额明显变化 | 本期/上期各至少5单；变化率绝对值≥30%；金额绝对差≥1000元 | 仅展示原值和可定义的算术比值，不判异常 |
| 订单数明显变化 | 本期/上期各至少5单；变化率绝对值≥30%；订单绝对差≥5单 | 同上 |
| 单日销售额集中 | 至少7个日历日、3个有销售日、本期至少5单；单日额严格大于2倍当期日均 | 不触发日额异常；零销售日仅作已查询数据描述 |
| 客户Top1集中度 | 本期至少5单、有客户成交；Top1金额/全厂同期间金额≥50% | 零分母或少订单不计算 |
| 客户Top3集中度 | 本期至少5单、至少4个成交客户；Top3金额/全厂同期间金额≥80% | 少于4个客户时展示可定义的占比，但不据此预警 |
| 低库存 | 当前数量严格小于该物料当前min_stock | 阈值仍由现有资料维护，不新增另一套库存标准 |
| 工单缺料 | READY_TO_ISSUE确认快照需求−当前发料仓余额，取max(差额,0)>0 | 已领料不重复补料；不支持历史库存还原 |
| 跨工具读时刻 | 绝对差≤60秒 | 超过则拒绝组合，不假装同一快照 |

规则是业务筛查，不是统计显著性检验或预测。补足最低库存阈值的参考数量与工单缺料是两种口径，分别说明，不能相加当采购计划。

## 客户集中度

支持“2026-10-01至2026-10-19客户集中度如何”。继续先用确定性日期解析；无范围时澄清日期。明确针对某个客户名称或ID的“集中度”先澄清为客户结构总体，不能静默改为全厂分析。显式“全厂/总体客户集中度”正常支持；整句（含指标后的限制语）都要检查，不能忽略后缀客户范围。未识别的范围表达会保守澄清，不声称覆盖任意自然语言。

使用现有`get_sales_summary`取得同期间全厂含税已发货销售单头金额，使用`get_customer_sales_ranking(limit=4)`取得Top1、Top3及至少第4名的存在证据；两者都需要销售读权限。分母绝不是前N名合计，也不累计商品订单数充当总体订单数。按后端客户ID识别对象，候选/ID仍不交给模型选择。

校验日期、币种、维度、来源、查询时刻、排序、重复ID、订单数及金额；前4客户金额/订单数合计不得超过总体，有正总额却无排行也视为矛盾。排行少于4且金额合计并不等于总体时，不能声称已覆盖完整客户结构，应澄清。跨工具查询没有共同事务快照，60秒只是组合读的时差上限；一致性核对不是并发写入期间的原子性保证。

## Reflection与故障

主销售路径现在先执行确定性检查，再调用模型Reflection：

- 核对工具种类、必要字段、指标定义/币种/维度、实际日期、每个日历日、金额合计、去重订单数合计和非负整数约束。无关库存载荷、错维度、重复/漏日或矛盾数值不能作为销售证据，即使模型允许report也拒绝。
- 缺少汇总或趋势，或缺少来源/查询时刻时，按剩余工具预算只补查缺失项，保留已验证结果；不为补缺而再次让模型选择身份/日期。
- 部分工具失败不是零；可在预算和总尝试次数内补查。全部查询失败返回错误。达到上限且仍缺必要证据时返回`clarification`，列出未回答工具与依赖它们的异常解释，能够独立确认的汇总同时注明范围、来源、时刻。
- 此澄清类型为`evidence`，上下文仅保留原范围、指标和缺失工具名称，不把失败响应或凭据存入会话。用户拒绝重试时不再调用模型或工具；同意后在原期间重新查询，不长期缓存上轮数值。
- 模型对完整数据仍提出retry时保留已有有界重规划机制。达到调用/反思上限必须说明尚未完成的核对，不能假装报告完成。
- 客户集中度使用同一个证据检查器；排行部分失败时有限补查，仍失败则澄清缺失的集中度证据。当前库存/缺料在确定性分支按同样的事实、假设、行动格式输出，不增加模型调用。

保留会话所有权、CSRF、服务认证、短期能力、固定工厂与各工具权限。SSE事件名和外部会话DTO不变；没有新的业务写接口。

## 验证与运行边界

默认`./scripts/Test-AiEvaluation.ps1`新增证据质量单元/图评测和`AiEvidenceIntegrationTest`。该集成测试先核对数据库为mini_mfg_test，用固定2405年期间和事务回滚销售夹具，通过现有Java公开服务生成真实工具输出；独立读取销售单头和余额/阈值，在测试代码中分别计算总额/订单/客户分组，再由实际Python EvidenceEngine核对。库存夹具不直写余额，不执行记账。不把这项“真实Java工具→Python引擎”验证称为真实模型或HTTP流式端到端。

覆盖空数据、少订单、零基数、阈值边界、单客户/少客户、错分母、矛盾总额/订单/日期/维度/读取时刻、缺少来源、工具部分失败、恢复补查、调用上限、拒绝重试，以及销售下降与当前缺货不能直接建立因果关系。新测试均固定日期或注入时钟，不以运行当天的业务数据作为预期。旧测试桩补齐真实接口既有的metadata和逐日零值，原金额/订单数断言保留；不是放宽生产检查来适应桩。

运行结果见[第5阶段评测报告](ai-evidence-report.md)。本阶段未重启或热更新现有开发进程；Python通常不启用自动reload，需要由运行方在合适时机重启才能加载新代码。代码/测试验证不等于8081/8091当前运行版本验收。真实模型仍需显式启用，测试桩不计真实模型验证。
